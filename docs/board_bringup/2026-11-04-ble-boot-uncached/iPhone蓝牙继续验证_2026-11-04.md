# iPhone 蓝牙继续验证

本轮在已验收的主动提醒固件上恢复 BLE 验证，不回刷旧 BLE 固件，不使用 API Key、不测试录音或外放。

## 初始状态

- COM5 可用，`focusmate_ble status` 为 daemon=0、host=0、advertising=0。
- UI 为 welcome，任务数 4，未开始专注计时。
- 预约数 0。当前固件仍为提醒功能验收版。

## 新发现的阻塞

执行历史验证方式 `focusmate_ble nocache` 时，在 `up_disable_dcache()` 后输出提示的 `puts → flockfile → nxrmutex_lock → nxmutex_wait` 路径触发 `/include/nuttx/semaphore.h:523` 断言。尚未打印缓存关闭成功提示，也未开始 BLE 广播。

此轮设备已运行一段时间且启动过提醒服务；不能据此确认是提醒功能导致异常。**已确认的是运行中关闭全局 D-cache 的诊断路径仍不稳定。** 先前电脑收发成功只证明当时的特定诊断状态，不代表默认缓存配置已修复。

随后用 sftool 自动复位并只读应用头，下载调试 stub 时超时，退出码 1。没有执行 `write_flash` 或擦除命令。复位后串口未恢复，已停止自动重试，并请用户短按 RESET。

## 下一步

1. 用户短按 RESET，确认 UI 与任务保留并恢复串口。
2. 在未重新启动预约服务时核对 BLE 初始化；若诊断路径仍异常，先修复缓存切换/共享区问题，不让用户在 nRF Connect 中反复尝试。
3. 确认板端广播就绪后，再由 iPhone 连接、读取身份、订阅通知、发送 `ping`，核对实际 `pong`。
4. iPhone 收发和重连成功后，才继续手机 HTTPS 中转。nRF Connect 本身不是联网网关。

证据：`output/validation/2026-11-04-iphone-resume/preflight.log`、`start.log`、`start-after-reset.log`。当前未取得新的 iPhone 收发结果，未上传 GitHub。

## 手动复位后的恢复与新修正版

用户按 RESET 后反馈黑屏，但 COM5 可响应 NSH，任务表中 UI 仍运行。通过 `focusmate_ctl home` 重绘后，用户已确认屏幕恢复，无需再次断电。

复位后任务数为 3。检查确认 `/data` 挂载类型是 **tmpfs**，所以此前新增的“写报告”测试任务未在复位后保留。前一阶段验证的是同一次运行内的文件写入与重载，不能视为掉电持久化。后续需要独立接入 Flash 文件系统；本轮不把此项混入 BLE 修复。

检查本地 NuttX `up_disable_dcache()` 实现发现，其关闭缓存及清理脏缓存行的过程中没有内部屏蔽中断。旧命令也没有在调用前加保护；存在被其他任务/中断打断的窗口。已为该诊断调用添加 `enter_critical_section()` / `leave_critical_section()`，临界区内不进行日志、分配或等待。该机制是本轮排查假设和修复尝试，编译通过不等于已证明消除了所有缓存问题。

新固件保留提醒、音频和 GPIO 功能；旧提醒验收固件仍保留。新产物及烧录/运行证据目录为 `output/firmware/2026-11-04/ble-cache-critical/`，真实实板验证结果待补充。此方案仍是全局关闭缓存的诊断绕行，尚未完成共享邮箱区域的局部缓存属性修复。

临界区修正版烧录校验成功，但先启动提醒服务、再调用 `nocache` 时仍触发 HardFault，任务表出现明显损坏。因此**临界区候选失败，不作为可用修复**。失败日志是该目录 `start-with-reminder-service.log`。这反驳了“只补防抢占保护即可解决”的假设，尚不能把异常归因于单一线程切换窗口。

已在后续源码中停用运行中关闭缓存的命令：有缓存配置时明确拒绝执行，避免反复触发异常。正在尝试 `CONFIG_ARMV8M_DCACHE=n` 的启动配置，保留 I-cache 和提醒功能；结果待编译及实板验证，不提前认定成功。

厂商 Kconfig 原本无条件选择 `ARMV8M_DCACHE` 与 `ARCH_DCACHE`，因此第一次仅改 `.config` 的尝试没有生效，已被生成配置断言拦截，未烧录。后续增加默认关闭的 `SF32LB52_DCACHE_BOOT_DISABLED` 诊断选项，使两项选择可条件关闭，并增加 `prepare_sf32_ble.py --cache-disabled-at-boot` 复现入口。

该配置还暴露本地 ARMv8-M 缓存 API 的链接问题：`cache.h` 在 I-cache 启用时声明 `up_coherent_dcache`，实现却仅在 D-cache 启用时编译。现将实现条件与 I-cache 声明条件对齐；无 D-cache 时清理宏为空操作，但仍执行 I-cache 失效。默认两种缓存都启用时行为不变。

最终构建已检查生成的头文件：D-cache 与 ARCH_DCACHE 均未定义，I-cache 保留。固件 `9ac29af15b1b85fd27b86871f0f1a6ff38b35150ca8e01abd1aabdb97ebe2bff`，3,157,668 字节。配置与源码检查通过，实板启动结果仍待验证；全局关闭 D-cache 有性能代价，不等于共享区域缓存属性问题已根治。

## 启动无 D-cache 版本的实板结果

- 烧录回读校验退出码 0。读取实际 CCR 寄存器为 `0x00020201`：bit16（D-cache）=0，bit17（I-cache）=1，与生成配置一致。
- 先启动提醒线程，再执行旧 `nocache` 命令，明确返回“D-cache disabled at boot; no runtime switch”，不再执行切换。
- 堆完整性检查通过，UI 为 standby、任务数 3，BLE 初始化与传统 NUS 广播成功。
- Windows 实际连接、读取身份、订阅后，连续 16 次 `ping/pong` 通过；断开后恢复广播。
- BLE 运行期间创建 3 秒“兼容验证”预约，实际出现 `FIRED` 和 `SHOWN`；测试提示已关闭，没有新增今日任务或启动专注计时。
- 最后板端 `host=1 advertising=1 connected=0 rx=16 tx=16 error=0`，`injected=0`，堆检查仍通过。电脑已释放连接，已请求用户用 iPhone 复测。

当前已烧录并保持运行的是 `ble-boot-uncached` 版本，临界区候选不再使用。iPhone 实际回复与手机 HTTPS 尚待验收，不能把电脑结果当成手机联网成功。今后重启时无需再关闭运行中的缓存；广播仍需 `focusmate_ble start` 启动。
